## Blackjack-step3

블랙잭에서 상태 패턴을 적용할 수 있는 대상은 `Player`가 가지고 있는 **`Hand`의 상태**라고 생각했습니다.
즉 **손에 들고 있는 카드의 상태에 따라 행동이 달라지고, 그에 따라 상태가 전이되는 구조**를 표현하려는 목적입니다.

상태 패턴을 적용하면 다음과 같은 구조로 표현할 수 있습니다.

```
Player
 └─ State (interface)
      ├─ Started (초기 상태)
      ├─ Running (히트 가능 상태)
      └─ Finished (종료 상태)
           ├─ Stay
           ├─ Bust
           └─ BlackJack
```

각 상태는 다음과 같은 전이를 가집니다.

```
Started → Running
Started → BlackJack (처음 두 장이 블랙잭)

Running → Running (히트 후 계속 진행)
Running → Stay (멈추기)
Running → Bust (버스트)
```

이 구조에서는 상태 전이와 행동을 **각 상태 객체가 직접 담당하도록 구성할 수 있습니다.**

---

# Step2 vs Step3 비교

## 기준

* **Step2**

  `HandCard` 객체에서 카드 점수를 계산하고
  조건문을 통해 현재 상태를 판단하는 방식

* **Step3**

  `State` 객체(`Started`, `Running`, `Finished`)가
  상태 전이와 행동을 직접 담당하는 방식

---

# Step2 방식이 더 적합할 것으로 보이는 경우

다음과 같은 상황에서는 상태 패턴을 사용하지 않는 구조가 더 단순할 수도 있다고 생각했습니다.

* 상태의 종류가 **적고 고정되어 있는 경우**
* 상태 전이 규칙이 **자주 변경되지 않는 경우**
* 상태별 행동이 **크게 복잡하지 않은 경우**

현재 블랙잭 기본 규칙에서는 상태가

```
Running
Stay
Bust
BlackJack
```

정도로 제한되어 있기 때문에
`HandCard`에서 점수를 계산하고 조건 분기로 처리하는 방식이 **구현과 이해 측면에서 더 단순할 것으로 예상됩니다.**

---

# Step3 방식이 더 적합할 것으로 보이는 경우

반대로 다음과 같은 상황에서는 상태 패턴이 더 도움이 될 수도 있다고 생각했습니다.

예를 들어

* `Split`
* `DoubleDown`
* `Surrender`

같은 규칙이 추가되면서 **상태 종류와 전이 규칙이 계속 늘어나는 경우**

또는

* 상태에 따른 행동 로직이 여러 클래스에 흩어지면서
* 조건 분기가 계속 증가하는 경우

이 경우에는 상태 패턴을 적용해
각 상태가 자신의 행동과 전이를 직접 관리하도록 하는 구조가
**코드 관리 측면에서 더 나을 가능성이 있다고 생각했습니다.**

---

# 결론

현재 과제 범위의 블랙잭에서는

> **Step2 방식(HandCard + 적은 조건 분기)** 이
> 구현 단순성과 코드 이해 측면에서 더 자연스러운 선택일 것으로 보입니다.

다만 게임 규칙이 확장되어 상태 전이가 복잡해지는 시점에는

> **Step3 방식(상태 패턴)** 으로 구조를 변경하는 것이
> 유지보수 측면에서 더 나은 방향이 될 가능성이 있다고 생각합니다.
